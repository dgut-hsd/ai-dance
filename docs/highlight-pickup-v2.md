# 摆摊现场取片：现状诊断与改造方案（v2）

面向场景：摊位上一台游戏机。顾客跳完 → 机器上回放高光 → 屏幕提示「完整高光请到工作人员处领取」
→ 顾客走到工作人员处 → 工作人员**收款** → 出示二维码 → 顾客扫码**下载**。

商业模型决定了整个设计：**这是付费交付，所以不能无人化。**
（v1 设想的「机器上直接出二维码自助下载」已否定：没人看着就等于免费送。）

---

## 零、先修：当前录不上了

`.highlight-data` 里 29 条任务的真实状态是 **uploading 20 / ready 9**，而 `POST /api/highlights` 的口径是：

```js
[...jobs.values()].filter(j => ['uploading','queued','processing'].includes(j.status)).length >= 20
```

20 >= 20 → **新任务全部 429**。客户端 `catch { return null; }` 把它吞掉了，所以现场表现是
「录制开关开着，跳完什么都没有」。这 20 条是历史上「开一局、没传完就关页/断网」留下的占位任务，
`uploading` 不占用单线程转码 worker 的任何能力，不该计入转码限流。

**已修**：限流只计 `queued`/`processing`；创建失败改为 `console.warn` 输出原因；补了回归测试。
（见 `server/app.js`、`web_dance/highlights.js`、`test/highlights.test.js`）

## 一、现场动线

```
顾客跳完
  └─ 机器自动回放 3 个最佳瞬间（本地原片，免费预览）
       └─ 屏幕常驻提醒：「这条高光，值得带回家 · 完整版请到工作人员处扫码领取」
            └─ 顾客走到取片台
                 ├─ 工作人员看缩略图认人（人脸 + 时间 + 成绩）
                 ├─ 点开卡片：播放确认 + 报价
                 ├─ 顾客扫工作人员的收款码付款（微信/支付宝，你自己手机上的，无需开发）
                 ├─ 工作人员点「已收款」→ 服务端解锁该视频
                 └─ 出示该视频的二维码 → 顾客扫码 → 直接下载 / 长按保存
```

关键点：**二维码本身不能是免费的入口**。未解锁时 `/api/highlights/:id/media` 必须拒绝，
否则顾客把链接转给别人就是白送。这是本方案唯一一处破坏性改动，见第五节。

## 二、屏幕上的提醒文案（重点）

### 文案结构

一段有效的提醒要同时说清三件事，缺一个就掉转化：

| 位置 | 作用 | 例 |
|---|---|---|
| 钩子 | 让他**想要** | 「这条高光，值得带回家」 |
| 价值 | 让他知道**拿到的是什么** | 「为你剪好的 9:16 竖屏成片 · 可直接发朋友圈」 |
| 动作 | 让他知道**去哪儿** | 「完整版请到工作人员处扫码领取 →」 |

两个写作原则：

- **不要出现「购买」「付费」「价格」字样**。一出现就把「纪念品」变成「商品」，摊位场景下掉单明显。
  用「带走 / 领取 / 收藏 / 带回家」。
- **真正的购买动机是「能发出去」**，不是「留个纪念」。顾客掏钱是为了发朋友圈/抖音被人看见。
  所以副标题里一定要点出「竖屏、可直接发」。

### 主推文案

**结算页常驻横幅（主文案）**

```
✨ 这条高光，值得带回家
   为你剪好了 9:16 竖屏成片 · 可直接发朋友圈
   完整版请到工作人员处扫码领取 →
```

**回放页角落（字数必须少，不能抢画面）**

```
完整高光 · 到工作人员处扫码领取 →
```

### 备选（建议现场 A/B）

| 风格 | 主文案 | 适用 |
|---|---|---|
| 社交驱动 | **发出去，让他们看看** | 年轻客群，动机最强 |
| 稀缺感 | **全场只有这一条** | 单人摊位、排队时效果好 |
| 成就延续 | **刚才那三下，值得留档** | 跳得好的顾客 |
| 直白高效 | **完整高光成片 · 工作人员处领取** | 中老年客群、看不懂隐喻时 |

### 位置与时机

- **回放页**：顾客正在看自己的片段，注意力最高，但只有几十秒。角落小字提示即可。
- **结算页**：回放结束后必须**常驻**一条横幅，因为顾客拍成绩照、看分数会停留很久。
- 顾客可能在回放中途就转身了 → 两个地方都要有，不能只放回放页。

### 价值对照（工作人员话术的基础）

免费和付费的东西必须在顾客心里分得开，否则他会觉得「我不是刚在屏幕上看到了吗」：

| | 机器上回放的（免费） | 付费拿到的成片 |
|---|---|---|
| 内容 | 原始录像片段 | 3 个最佳瞬间，卡点剪辑 + 片头 + 成绩卡 |
| 画幅 | 页面尺寸 | 1080×1920 竖屏，专为手机 |
| 用途 | 看一眼 | 直接发朋友圈 / 抖音 |

**工作人员话术**：「这条已经剪好了，竖屏的，直接能发抖音，¥19.9 带走。」
一句话里给到：已完成（不用等）、可用（能发）、价格（不用问）。

价格建议现场定档，摊位上常见的两档结构：单条 ¥19.9 / 三首打包 ¥39.9。价格显示在二维码旁边比口头报价好，
能减少讨价还价。

## 三、缩略图（工作人员认人用，必需）

### 为什么不能直接用 `poster.jpg`

`poster.jpg` 是成片第 0 帧，而第 0 帧属于片头。实测三条真实任务：

- `.highlight-data/9o6fP3EzeXEKZ-I4pq2ObgAqNyO5oVxx/poster.jpg` → 有真人 ✅
- `.highlight-data/lXs-7lx67w11gu6oo07AIc52MKPMXPp7/poster.jpg` → 有真人 ✅
- `.highlight-data/DE5EMP8pXkhMqFvGuAE9lxsQyJZuBBpD/poster.jpg` → **片头动画角色** ❌

所以必须专门抽一帧。

### 怎么抽

在 `server/media.js` 的 `makeVideo` 里多产出一张 `thumb.jpg`：

```
-ss <正片内的时间点> -i output -frames:v 1 -vf scale=360:-2 -q:v 4 thumb.jpg
```

**抽哪一帧**：优先取 `story.segments[0].peak` —— 顾客表现最好的那个瞬间的中点。
既避开了片头，又最可能是「人站得正、表情好」的一帧。退化方案是 `introDuration + 2`。

### 显示

- 卡片用的缩略图建议 `object-fit: cover; object-position: center 40%`，当前 layout 下真人铺满整屏，脸部偏上。
- 缩略图尺寸要**大**：一屏 6 张、每张宽度 ≥ 320px。想靠它认脸，小图没有意义。
- 权限与 `poster` 一致（按随机 id 公开）。理由：顾客也要在领取页看到这张图来确认「这是我」，
  而 `poster.jpg` 本来就已是这个权限等级，不新增暴露面。

### 缩略图之外的认人手段

1. **时间**：卡片显示「3 分钟前」，1 台机器的摊位，取片台前的人几乎总是**最新那条**。
   所以默认排序必须是最新在前，且新任务不能把已渲染的卡片挤走（见第四节第 5 点）。
2. **取片号**：每局一个短号（`#014`），顾客在机器上看到过、工作人员按号定位，不依赖脸。
   代价是服务端要持久化 `seq`，且**短码只能让工作人员输入，不能做成顾客自助查询**（4 位可枚举）。
3. **成绩**：顾客通常记得自己跳了多少分，可作为二次确认。

## 四、取片台（工作人员那台机器）

1. **默认只显示待取**：`ready` 且未解锁的，按时间倒序。其余折叠进「今日已售 / 未完成」两个可展开区。
   这一条单独就能把 29 张卡变成 3～5 张。
2. **大缩略图卡片**，一屏 6 张：图 + 「3 分钟前」+ 成绩 + 时长 + `#序号`。
3. **点开卡片 = 全屏交付视图**：
   - 左侧：内嵌播放完整成片，让顾客先看完再决定（成交率的关键）
   - 右侧：价格 + **「已收款，解锁」大按钮**
   - 解锁后：同一个位置显示两张直下二维码（SHORT 传播高光 / LONG 完整纪念版，大，占屏高 60%+）
4. **交付后点「已取走」** → 卡片移入「今日已售」，顶部显示 `今日 12 条 · ¥238`。
   摆摊老板需要这个数字，顺便让待取区保持干净。
5. **修掉每 4 秒整表重建**：`staff.js` 的 `render()` 现在是 `innerHTML = ""` 全量重建 + `setInterval(refresh, 4000)`。
   新任务插到最前会把所有卡片推走一格 —— 工作人员手指底下的卡片会在点击瞬间移位，直接点错人。
   改为按 `id` 复用节点、刷新间隔放宽到 8～10s、新任务只做一次高亮提示。
6. **现场模式**：一个极简手机/平板视图，只有「最近 5 条」+ 大缩略图 + 全屏二维码。
   工作人员拿着平板走到顾客面前出示，比让一圈人挤到电脑前好得多。
7. **生成中要有进度**：单 worker 串行转码一条要几十秒。卡片显示「生成中 · 约 40 秒」，
   工作人员可以据此决定先收钱还是让顾客稍等。

## 五、支付与解锁（安全核心）

### 推荐：先收款，后解锁（零支付集成）

1. 工作人员用自己的微信/支付宝收款码收钱（贴台面上或手机出示，不需要任何开发）。
2. 点「已收款」→ `POST /api/highlights/:id/unlock`（带 `X-Owner-Token`，工作人员本来就有）→ 写 `paidAt`。
3. 服务端从此允许 `GET /:id/media` 通过；**在此之前必须 403**。

这是唯一一处破坏性改动：现在 `/v/:id` 和 `/media` 是「拿到链接就能免费看」。
不加上这道门，付费模式在技术上不成立。

### 二维码指向哪里

**指向直下地址，不要指向领取页。**（2026-09 现场定版：原先设想的「领取页中转」已否定。）

一张卡同时给两张码，顾客自己选：

| 码 | 后缀 | 内容 | 适合 |
|---|---|---|---|
| SHORT | `short.mp4` | 3 段最佳动作卡点剪辑，约 20 秒 | 发朋友圈 / 抖音，扫码即下 |
| LONG | `long.mp4` | 整段真人录像 + 片头成绩卡 | 想留全场的人 |

理由：① 顾客站在柜台前的耐心只有几秒，「扫码 → 页面 → 再点下载」多一步就掉单，直接下载
才是把「已经付过的钱」变成「手机里的文件」的最短路径；② 两张码让顾客按场合自选，不必再问
工作人员「有没有完整版」；③ 页面上的成绩、缩略图这套说辞在收款前就已经讲完，交付环节不需要再演一遍。

代价与对策：

- 微信内直接下 MP4 可能失败 → 码旁边保留桌面浏览器兜底（后台同时给出 `<a>` 直链，工作人员可发链接），
  码下方印一行「微信里打不开就用浏览器扫」。
- 直链会暴露 OSS 签名 URL → 签名有效期跟着 `expiresAt` 走，且只在解锁后签发；未解锁时
  `/api/highlights/:id/media` 与 `/full-media` 必须拒绝，`/qr-short`、`/qr-long` 也一样。
- 完整版没转完时不能给码 → `/qr-long` 在 `fullStatus !== 'ready'` 时返回 409，
  后台弹窗显示「完整视频生成中，就绪后二维码会自动出现」，绝不生成一个扫了才发现没文件的码。
- 领取页 `/v/:id` 仍然保留，作为「观看 / 补下载 / 换手机」的入口，但不再是交付主路径。

未解锁时，领取页只显示成绩 + 缩略图 + 「请到工作人员处开通」，不显示完整播放。

### 防泄漏

- 解锁后才可访问 `/media`。
- OSS 模式的签名有效期现在跟着 `expiresAt` 走（最长 24 小时）。付费场景建议缩短到 1～2 小时 ——
  顾客都是现场下载，没理由让链接长期有效。
- 可选：解锁后生成的领取码 10 分钟失效，进一步降低转发的价值。

### 将来要放大的话

「扫码 → 页面内直接微信/支付宝支付 → 自动解锁」是更顺的体验，但需要商户号、H5 支付、
异步回调与对账，摆摊阶段不值得做。先跑通线下收款，验证成交率。

## 六、顾客扫码后看到什么（领取页）

- 未解锁：缩略图 + 成绩 + 「请联系工作人员开通」。
- 已解锁：完整视频 + 大号「下载高清成片」按钮 + 微信引导。
- **把领取记录存 localStorage**：现在 `/v/:id` 是 32 位随机串，顾客随手关掉页面就永远找不回去了。
  在页面底部加一块「本机最近领取」，零后端成本。
- **微信 UA 检测**：顾客几乎全用微信扫一扫，而微信里下载 MP4 大概率失败。
  现在 `highlight.html` 只有一行小字提示，应改成显眼浮层引导「在浏览器打开」或「长按视频保存到手机」。

## 七、状态与接口改动清单

| 改动 | 位置 | 说明 |
|---|---|---|
| `thumb.jpg` | `server/media.js` | 正片内抽帧，见第三节 |
| `GET /:id/thumb` | `server/app.js` | 同 `poster` 权限 |
| `POST /:id/unlock` | `server/app.js` | 工作人员标记已收款，写 `paidAt` |
| `POST /:id/delivered` | `server/app.js` | 已交付，写 `deliveredAt` |
| `GET /:id/media` 加门禁 | `server/app.js` | 未 `paidAt` → 403（**破坏性**） |
| `seq` | `POST /api/highlights` | 当天局号，机器端与取片台共用 |
| `GET /api/highlights` | `server/app.js` | 返回 `thumbUrl` / `paidAt` / `deliveredAt` / `seq` |
| 价目档位 | 取片台本地配置 | 单条 / 打包，显示在二维码旁 |
| 结算页横幅 | `web_dance/dance.html` + `main.js` | 常驻，见第二节 |
| 回放页角标 | `web_dance/main.js` | 小字提示 |

## 八、边界情况

| 情况 | 处理 |
|---|---|
| 顾客不肯买 | 卡片留在待取区，加「顾客放弃」标记；7 天后随任务过期自动清理 |
| 出片还没好就要付钱 | 可以收，给码后顾客扫到「剪辑中，1 分钟后自动出现」，领取页本来就在轮询 |
| 生成失败 | 取片台给一键重试；已收钱的必须当场处理，别让顾客等 |
| 顾客手机没电 / 没微信 | 工作人员可代为下载后微信/AirDrop 发给顾客；取片台的「在电脑上下载」保留 |
| 顾客已离场才出片 | 待取区保留 7 天，但现场基本追不回来 —— 这也是要尽量缩短转码时间的原因 |
| 转码提速 | `preset medium → veryfast`（CRF 不变，画质损失很小）可快 2～4 倍，直接减少顾客等待与流失 |

## 九、建议落地顺序

1. **已完成**：修 429，恢复录制能力。
2. **缩略图**（`thumb.jpg` + 取片台大图卡片）—— 这是「认人 + 提高成交」的最高性价比一步。
3. **屏幕提醒横幅** —— 零风险，直接影响进店率。
4. **收款解锁门禁 + 全屏交付视图** —— 让付费模式在技术上成立。
5. **领取页找回 / 微信引导** —— 降低现场投诉。
6. 取片号、交付统计、转码提速。

## 十、验收

- 未解锁时 `/api/highlights/:id/media` 返回 403，领取页不显示完整播放。
- 解锁后顾客扫码能正常播放与下载；微信内能走通长按保存或浏览器打开。
- 取片台缩略图里能看到人脸（不是片头动画角色）。
- 新任务出现时，已渲染卡片位置不动。
- 交付后卡片离开待取区，今日统计数字正确。
