# DANCE ARENA 产品路线图(摄像头跟跳音游)

> 定位:打开网页 + 摄像头,跟着 3D 舞者跳,实时打分,想再来一局。
> 受众:想动一动的普通用户(有摄像头、有浏览器即可)。
> 本文档是「从技术 demo 升级成可玩音游」的执行路线图,按**杠杆从高到低**排序。

---

## 0. 北极星指标与核心闭环

### 0.1 一句话定位

> 任何人打开网页、对准摄像头,就能跟着 3D 教练跳一支舞,获得即时的节奏判定与分数,并「想再来一局」。

### 0.2 北极星指标(唯一关键数字)

**再玩率(again-rate):完成一局的用户中,点了「再来一次」的比例。**

- 为什么是它:对一个单人开发、暂时没后台统计的项目,它是**唯一能被你直接观察**的指标——找个真人玩完,看他有没有主动点「再来」。
- 所有功能开发前先问:**它会让「再来一次」变高,还是让「做内容」变便宜?** 两样都不沾就不做。

### 0.3 核心闭环(Golden Loop)

```
选歌 → 看提示(动作卡片 + 3D 教练)→ 跟跳(动捕实时打分)→ 结算(看清自己跳得怎样)→ 再来一次
```

**这个闭环必须 100% 走通,才叫「游戏」;现在它断了三处(见 Phase 1)。**

---

## 1. 分层模型(决定优先级)

| 层 | 作用 | 现状 | 优先级 |
|---|---|---|---|
| **核心循环** | 让一局「看得懂、玩得爽、有结果」 | 判定内核有,视觉/结算缺失 | **P0** |
| **内容** | 决定能不能留住(曲库/谱面) | 只有 1 支手写 demo | **P0** |
| **元游戏** | 决定能不能长期玩(选曲/存档/难度) | 空白 | P1 |
| **精度/体验** | 手感上限(延迟/性能/跳跃) | 有基础,待打磨 | P1 |
| **增长/发行** | 传播(分享/排行/多人) | 空白 | P2 |

---

## 2. Phase 1(P0)—— 让核心循环「看起来像个游戏」

> 目标:把「跟跳 demo」变成「看得懂、有结果、想再来」的音游。**这一阶段做完,项目从「技术验证」跨进「可玩原型」。**
> 预计:2–3 周。

### 1.1 动作预期卡片(Just Dance 式右侧滚动列)✅ 已完成

**为什么**:跟跳游戏缺的是「预判」——玩家永远在「被动跟、看到才反应」。Just Dance 用「动作提示卡片」提前展示接下来的动作,让玩家能提前准备。**本游戏考的是「动作像不像」,不是「按键时机」,所以不用下落音符轨道(那是 DDR 类节奏游戏的机制),用 Just Dance 式动作卡片。**

**做什么**:
- 右上角「目标动作」下方新增一条竖直滚动列,展示接下来 3 个动作的火柴人卡片。
- 卡片随歌曲时间向上滚动(动作时刻越近越靠近顶部判定线),最近的一个高亮 + 显示倒计时秒数。
- 动作时刻来源:优先谱面 `chart/v1` 的音符;无谱面时按固定间隔(2s)生成。

**动文件**:`web_dance/index.html`、`web_dance/style.css`、`web_dance/main.js`。

**验收**:
- [x] 挑战模式右上角能看到接下来 3 个动作的卡片向上滚动。
- [x] 最近的动作卡片高亮并显示倒计时,到点与教练动作对齐。
- [x] 加载无 chart 的参考 JSON 时,回退为固定间隔展示,不报错。

### 1.2 判定结果闭环进结算界面

**为什么**:你现在已经用 `NoteJudge` 统计了 PERFECT/GREAT/GOOD/MISS,但结算界面只显示了 `SimpleScorer` 的连续相似度 grade——**音符层的努力全部被浪费**。这是「调判定手感时没有真实依据」的根源。

**做什么**:
- 结算界面新增:音符判定统计(PERFECT/GREAT/GOOD/MISS 计数)、音符准确率、与连续相似度两套分数并列展示。
- 明确两套分数如何合成一个「总分」(建议:连续相似度 = 基底分,音符 = 节奏 bonus,现有 `noteBonus` 已在做,补全展示)。

**动文件**:`web_dance/main.js`(`finishChallenge`)、`web_dance/index.html`(结算面板)。

**验收**:
- [ ] 结算界面能同时看到「动作匹配度」和「节奏命中」两套结果。
- [ ] 打同一支舞两次,一次跟准节拍、一次乱跳,结算能明显区分。

### 1.3 把 `Scheduler` 真正接入主流程(修掉「造了没用的机器」)

**为什么**:你写了 `Scheduler`(有单测),但 `main.js` 的倒计时还在用 `sleep()`+`setTimeout`,音符判定也是每帧直驱。这是「技术债 + 手感隐患」双重问题:`setTimeout` 漂移会污染你辛苦做的单一时钟。

**做什么**:
- 倒计时 3/2/1/GO 改用 `Scheduler` 绝对时间排程(设计稿 `audio-engine-api.md` §7 已经写清楚了改造点)。
- `SongSession.update()` 内走 `Scheduler.start()` 的 25ms tick,而不是只靠 rAF 每帧驱动(避免 rAF 被节流时漏判定)。

**动文件**:`web_dance/main.js`(`countdownTo` / `onFrame`)、`web_dance/audio.js`(`SongSession`)。

**验收**:
- [ ] 倒计时与音频起点严格对齐,GO 时刻 = songTime 0.000s。
- [ ] 后台切走再切回,音符判定不丢、不错位。

## 3. Phase 2(P0)—— 内容管线:让内容从 1 变 10

> 目标:一支手写 demo 舞 → 一个能批量产谱面的管线。**没有这一步,你永远是「demo」,不是「游戏」。**
> 预计:2–3 周。

### 2.1 离线谱面生成脚本(视频 → 契约帧 → 参考 JSON 自动化)

**为什么**:`interface-contract.md` 里的「FBX → 渲染 MP4 → MediaPipe → 参考 JSON」离线流程**只写在文档里**,没有自动化工具。内容从 1 变 10 卡在这。

**做什么**:
- 做一个 Node/CLI 或网页工具:`tools/` 下新增脚本,输入一段舞蹈视频(或 FBX 渲染出的 MP4),输出标准 `dance-sequence/v1` JSON。
- 复用 `pose_capture/export.js` 的逐帧逻辑(改手动 seek 循环,支持固定 fps、加速导出)。

**动文件**:新增 `tools/build-sequence.mjs`(或复用 `pose_capture/export.js`)。

**验收**:
- [ ] 喂一段真人/3D 跳舞视频,自动产出合法 `dance-sequence/v1` JSON。
- [ ] 产出 JSON 能被挑战模式直接加载并正确回放教练动作。

### 2.2 最简谱面编辑器(手动打点即可,不要做全功能编辑器)

**为什么**:谱面(哪些时刻有音符)不能只靠代码手写。但**别做全功能编辑器**——先做一个「在时间轴上点击埋音符 → 导出 chart JSON」的最简工具,能干活就够。

**做什么**:
- 一个极简页面:加载参考序列 + 音频,播放时按空格/点击在时间轴打点,标注 lane/type,导出 `chart/v1`。

**动文件**:新增 `web_dance/chart-editor/`(独立页面)。

**验收**:
- [ ] 能对着音乐手动打点,导出合法 `chart/v1` 谱面。
- [ ] 导出的谱面能被挑战模式加载并触发判定。

## 4. Phase 3(P1)—— 元游戏:让玩家「想再来」

> 目标:一局玩完有「下一局」的入口和理由。
> 预计:2 周。

### 3.1 选曲界面

- 一个曲目列表(哪怕 3–5 首),显示歌名/难度/BPM/最高分,点选进入。
- 动文件:`web_dance/index.html` + 新增曲目注册表。

### 3.2 本地存档与最高分

- `localStorage` 存每首歌的最高分/最佳评级,选曲界面显示。
- 动文件:`web_dance/main.js` + 新增 `web_dance/storage.js`。

### 3.3 难度分级

- 用 `difficulty`(1–5)给每支舞标难度,同曲可有多难度谱面。
- 先做「简单标注 + 选曲筛选」,不做自动分级算法。

**验收(Phase 3)**:
- [ ] 用户能选歌、看到历史最高分、选难度,玩完回选曲界面再玩。

---

## 5. Phase 4(P1)—— 精度与体验:手感上限

> 目标:把「能玩」磨成「手感好」。持续迭代,不一次性做完。

### 4.1 延迟校准 UI
- 把 `LatencyModel.autoCalibrate` 暴露成一个校准流程(跟节拍敲击 → 自动算 offset),修掉 `interface-contract.md` §6 里标「待定」的 offset。

### 4.2 MediaPipe 迁 Web Worker
- 主线程推理会卡,污染单一时钟下的判定体验。用 Vite 打包迁到 Worker(README 已承认这是已知取舍)。

### 4.3 rootPos 位移(跳跃)✅ 已按方案 C 落地
- 契约帧目前丢弃髋位移,跳跃/前后移动无法还原。→ 已改为「根速度 + 地面接触」方案 C:
  - 生产端 `pose_capture/root-motion.js` 输出 `rootVel`(髋中点相邻帧差分)+ `grounded`(最低脚踝相对地面)。
  - 消费端 `retarget.js` 积分水平速度得到前后/左右位移,垂直在贴地时用运动学(蹲下)、腾空时用速度积分(跳跃)。
  - 参考/教练固定站位(`rootMotion:false`),评分仍只比对 `bones`,保持平移不变。

### 4.4 手势舞完整 retarget
- 手指逐节驱动(`hands` 21 点已有数据,`retarget.js` 未消费),`gesture` 音符的语义匹配(`gestureId`)。

## 6. Phase 5(P2)—— 增长与发行(暂缓)

- 录屏/分享 GIF(传播)
- 排行榜(后端,依赖服务端)
- 多人对战/同屏比舞(依赖网络架构)
- 真实版权曲库(依赖内容合作)

> 这些**在没有稳定再玩率之前一律不做**——它们是放大器,不是地基。地基不牢,放大的是「没人玩」这件事。

---

## 7. 明确的「不做」清单(防止再次迷茫)

以下东西在你达到「再玩率稳定 > 30%」之前,**一律不做**:

- ❌ 全功能谱面编辑器(先做最简打点版)
- ❌ 自动难度分级算法(先手动标)
- ❌ 排行榜/多人/后端(依赖服务端,且没有用户)
- ❌ 更复杂的评分算法(先把手感数据闭环,再调参数)
- ❌ 打包/部署/域名/多语言(先 localhost 找真人玩)

---

## 8. MVP 的完成定义(Definition of Done)

当下面**全部**为真时,你的项目就是「可玩的音游 MVP」,不再是 demo:

1. 用户打开页面,能看到动作卡片、3D 教练,跟着音乐跳。
2. 跳完能看到「动作匹配度 + 节奏命中」两套清晰结果。
3. 有 5 首以上曲目可选(内容管线能持续生产)。
4. 最高分被记住,选曲界面能看到。
5. **一个真实的人玩完,主动点了「再来一次」。**

---

## 9. 一句话总结

> **你已经把「难的部分」做完了(动捕/重定向/单一时钟/判定)。**
> **接下来只做两件事:① 让核心闭环「看得见、有结果」(Phase 1);② 让内容能批量生产(Phase 2)。**
> **其余全部排在「有真实用户反馈」之后。**
